# SDD+TDD 蓝绿迭代开发工作流

你正在执行一个 **先理解、再规范、TDD Red-Green 反馈循环驱动的自动化开发流程**。

## 核心概念

```
┌───────────────────────────────────────────────────────────────────┐
│                    蓝绿迭代开发循环 (Blue-Green Loop)                │
│                                                                   │
│  🧠 BRAINSTORM (苏格拉底式理解)                                    │
│  ┌─────────────────────────┐                                      │
│  │ 深度理解项目现状          │  ← 高交互：每次只问一个问题             │
│  │ 苏格拉底式提问挖掘需求     │                                      │
│  │ 探索 2-3 种技术方案       │                                      │
│  │ 产出：设计共识             │                                      │
│  └───────────┬─────────────┘                                      │
│              │ 用户确认设计                                         │
│              ▼                                                     │
│  🔵 BLUE (OpenSpec 规范产出)                                       │
│  ┌─────────────────────────┐                                      │
│  │ proposal / design       │  ← 低交互：一次性审查确认               │
│  │ tasks / specs delta     │                                      │
│  └───────────┬─────────────┘                                      │
│              │ 用户确认 → 进入全自动模式                             │
│              ▼                                                     │
│  🟢 GREEN (TDD Red-Green 反馈循环全自动执行)                         │
│  ┌──────────────────────────────────────────────┐                 │
│  │     每个 micro-task = 一次完整 TDD 循环        │                 │
│  │                                              │                 │
│  │   🔴 RED        🟢 GREEN       🔵 REFACTOR   │                 │
│  │   写失败测试  →  最小代码通过  →  清理重构     │                 │
│  │      │              │              │         │                 │
│  │      └── 必须失败 ──→└── 必须通过 ──→└── 必须全绿│               │
│  │                                              │                 │
│  │   task 完成 → auto review → auto fix → commit │               │
│  │   → 下一 task → 循环直到全部完成               │                 │
│  └──────────────────────────────────────────────┘                 │
│              │                                                     │
│              ▼                                                     │
│  🔵 归档 → 询问：目标达成？ → 未达成则回到 🧠 或 🔵 开始下一轮        │
└───────────────────────────────────────────────────────────────────┘
```

## 工作流步骤

### Step 0: 环境初始化（自动化，静默执行）

```bash
which openspec && echo "✅ OpenSpec" || echo "❌ 安装: npm install -g @fission-ai/openspec@latest"
ls openspec/specs/ 2>/dev/null && echo "✅ openspec/" || mkdir -p openspec/specs
```

读取项目关键文件以建立上下文（`pyproject.toml`、API 路由、数据模型、目录结构、现有 specs）。

---

### 🧠 Step 1: BRAINSTORM — 苏格拉底式深度理解

**必须先使用 `superpowers:brainstorming` 技能。**

**目标：在写任何规范之前，通过苏格拉底式提问彻底理解项目现状和用户意图。**

#### 1.1 项目现状理解

先自行探索项目（代码结构、已有功能、数据模型、技术约束），然后向用户确认理解：

> "我理解当前项目是 [技术栈]，已有 [功能列表]。对吗？"

#### 1.2 苏格拉底式需求挖掘

遵循 brainstorming 技能的铁律：**每次只问一个问题**。

提问策略（按顺序，每次一问）：
1. **目标澄清**：你想实现什么？解决什么问题？
2. **用户场景**：谁会用到这个功能？在什么场景下？
3. **范围边界**：什么属于这次范围？什么明确不做？
4. **约束条件**：有什么技术栈限制？性能要求？兼容性约束？
5. **优先级**：如果只能做一件事，哪件最重要？

每轮只问一个问题，根据回答决定下一问。不跳过、不合并。

#### 1.3 技术方案探索

**必须提出 2-3 种技术方案**，说明 trade-off，并推荐一种：

```
方案 A: [描述]  — 优点: ...  缺点: ...
方案 B: [描述]  — 优点: ...  缺点: ...
方案 C: [描述]  — 优点: ...  缺点: ...

我推荐方案 X，因为 [理由]。你觉得呢？
```

#### 1.4 设计确认

提出设计共识要点（200-300 字），逐节确认：架构思路、数据流、涉及文件、边界情况、验证策略。每节询问"这里对吗？"

**不可跳过用户确认**。

---

### 🔵 Step 2: BLUE — OpenSpec 规范产出

**基于 Step 1 的共识，创建正式规范文档。**

#### 2.1 生成 OpenSpec 文件

```
openspec/changes/<change-id>/
├── proposal.md    — 变更描述（动机、内容、影响范围）
├── design.md      — 技术设计（架构决策、数据流、索引策略）
├── tasks.md       — 任务清单（粗粒度，供 writing-plans 细化）
└── specs/         — 规格 delta（需求变更 diff）
```

#### 2.2 一次性审查

展示 4 份文档摘要给用户，**一次性确认**：

```
📄 proposal.md: [一句话摘要]
📄 design.md:   [技术方案摘要]
📄 tasks.md:    [共 N 个任务]
📄 specs/:      [X 条新增/修改需求]

确认后进入 TDD Red-Green 全自动执行模式。
```

**用户确认后即进入全自动模式，后续不再主动询问，除非遇到阻塞。**

---

### 🟢 Step 3: GREEN — TDD Red-Green 反馈循环全自动执行

**核心：整个过程由 TDD Red-Green 反馈循环驱动。零交互，异常时才暂停。**

#### 3.1 细化计划

使用 `superpowers:writing-plans` 将 OpenSpec tasks 转化为 bite-sized 实现计划（每个 task 2-5 分钟），保存到 `docs/plans/YYYY-MM-DD-<feature>-plan.md`。

每个 task 包含完整的 RED 阶段代码（失败的测试）和 GREEN 阶段代码（最小实现），以及精确的验证命令和预期输出。

#### 3.2 创建隔离工作空间

使用 `superpowers:using-git-worktrees`。

#### 3.3 核心引擎：TDD Red-Green-Refactor 反馈循环

**这是整个自动化执行阶段的心脏。** 每个 micro-task 严格遵循以下循环，使用 `superpowers:test-driven-development`：

```
┌──────────────────────────────────────────────────────────────┐
│              TDD Red-Green-Refactor 反馈循环                   │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │                   🔴 RED Phase                        │   │
│  │                                                      │   │
│  │  1. 写一个最小失败的测试                               │   │
│  │  2. 运行测试 → 必须失败                                │   │
│  │  3. 确认失败原因 === "功能未实现"（不是语法错误）        │   │
│  │                                                      │   │
│  │  ⛔ 测试通过了？→ 说明测试没测到东西，重写测试            │   │
│  │  ⛔ 测试报语法错误？→ 修复测试代码，重新运行              │   │
│  │  ✅ 测试因"功能未实现"失败 → 进入 GREEN               │   │
│  └──────────────────────┬───────────────────────────────┘   │
│                         │ 反馈：失败 ✓                        │
│                         ▼                                    │
│  ┌──────────────────────────────────────────────────────┐   │
│  │                  🟢 GREEN Phase                       │   │
│  │                                                      │   │
│  │  4. 写最少代码让测试通过（YAGNI，不多写一行）            │   │
│  │  5. 运行测试 → 必须通过                                │   │
│  │  6. 运行全部测试套件 → 必须全绿                         │   │
│  │                                                      │   │
│  │  ⛔ 测试失败？→ 修代码，不修测试                         │   │
│  │  ⛔ 其他测试被破坏？→ 立即修复                           │   │
│  │  ✅ 全部通过 → 进入 REFACTOR                          │   │
│  └──────────────────────┬───────────────────────────────┘   │
│                         │ 反馈：通过 ✓                        │
│                         ▼                                    │
│  ┌──────────────────────────────────────────────────────┐   │
│  │                🔵 REFACTOR Phase                      │   │
│  │                                                      │   │
│  │  7. 清理代码：去重、改善命名、提取公共方法               │   │
│  │  8. 运行测试 → 必须保持全绿                             │   │
│  │  9. 不添加任何新行为（YAGNI）                           │   │
│  │                                                      │   │
│  │  ✅ 保持全绿 → COMMIT                                 │   │
│  └──────────────────────┬───────────────────────────────┘   │
│                         │                                    │
│                         ▼                                    │
│                    📝 git commit                             │
│                         │                                    │
│                         ▼                                    │
│              下一个 task → 回到 🔴 RED                       │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              自动化 Review 闭环                        │   │
│  │                                                      │   │
│  │  每完成一个 task:                                      │   │
│  │  • 自动 spec review（代码是否满足规范？）                │   │
│  │  • 自动 code quality review（代码质量是否过关？）        │   │
│  │  • Review 发现问题 → 自动修复 → 重新 review              │   │
│  │  • 统计：✅ 通过 / ❌ 修复 / 🔄 重试次数                 │   │
│  └──────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

#### TDD 铁律（违反即 STOP，权重最高）

| 违规行为 | 后果 |
|----------|------|
| 在 RED 测试之前写实现代码 | **删除实现代码，从 RED 重来** |
| RED 阶段测试直接通过 | **测试无效，重写测试** |
| GREEN 阶段修改测试而非代码 | **回退，修代码** |
| REFACTOR 阶段测试变红 | **回退 refactor，定位问题** |
| 声称完成但未运行 `pytest` | **不可接受，立即运行验证** |
| 跳过某个 phase（"这次简单"） | **禁止，任何理由都不行** |

#### 3.4 全自动编排

使用 `superpowers:subagent-driven-development`（默认，不询问用户）：
- 每个 task 派发独立 implementer subagent，subagent 内部严格执行上述 TDD 循环
- Task 间自动 spec compliance review + code quality review
- Review 发现 issues → 自动回 implementer 修复 → 重新 review → 直到通过
- 所有 review 通过后自动 `git commit`
- 使用 `superpowers:verification-before-completion` 作为每次 commit 前的闸门

#### 3.5 异常处理 — 唯一暂停点

**仅在以下情况暂停并询问用户：**

| 异常类型 | 触发条件 | 处理方式 |
|----------|----------|----------|
| 依赖缺失 | pip/npm 包不存在 | 报告缺失内容，询问是否安装 |
| RED 卡死 | 同一 task RED 重复 3+ 次未通过 | 报告测试代码，请求指导 |
| GREEN 卡死 | 同一 task GREEN 重复 5+ 次未通过 | 报告失败详情，提供 2-3 条可能方向 |
| 设计冲突 | 实现与现有代码不可调和冲突 | 报告冲突点，提供 A/B 方案 |
| spec review 不通过 | 修复 3 次后仍未满足 | 报告 spec gap，请求确认是否放宽 |

**以下情况绝不暂停（自动继续）：**
- RED 测试首次失败 → ✅ 预期行为，自动进 GREEN
- GREEN 1-4 次失败后成功 → ✅ 正常调试
- 子代理自行修复 review 问题 → ✅ 自动化闭环
- 非破坏性警告（deprecation 等）→ ✅ 记录但继续
- REFACTOR 测试临时变红又恢复 → ✅ 正常重构
- 依赖包缺失 → ✅ 自动安装

#### 3.6 交互测试 & 功能验证自动闭环 (Auto-Healing Test Loop)

**目标：所有实现 task 完成后，自动发现测试问题、自动修复、自动验证，闭环直到全绿。**

```
┌──────────────────────────────────────────────────────────────────┐
│               交互测试自动闭环 (Auto-Healing Loop)                  │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  Phase 1: 全量单元测试                                      │   │
│  │                                                          │   │
│  │  1. 运行: uv run pytest tests/ -v                         │   │
│  │  2. 全部 PASS → 进入 Phase 2                              │   │
│  │  3. 有 FAIL → 进入自动诊断修复                             │   │
│  └──────────────────────┬───────────────────────────────────┘   │
│                         │                                        │
│                         ▼                                        │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  自动诊断修复循环 (max 5 次迭代)                            │   │
│  │                                                          │   │
│  │  对每个失败测试:                                           │   │
│  │  a. 读取失败测试代码 + 错误堆栈                             │   │
│  │  b. 分类问题类型:                                          │   │
│  │     • 测试代码过时（测试与新代码不匹配）→ 自动更新测试       │   │
│  │     • 实现代码 bug → 自动修复实现代码                       │   │
│  │     • 缺少 import/dependency → 自动补充                    │   │
│  │     • Mock/Stub 不匹配 → 自动更新 mock                     │   │
│  │  c. 修复后重新运行该测试                                    │   │
│  │  d. 通过 → 处理下一个失败                                   │   │
│  │  e. 仍失败 → 重试（最多 3 次同一问题）                       │   │
│  │                                                          │   │
│  │  ⛔ 同一问题 3 次修复失败 → 暂停，报告用户                   │   │
│  │  ⛔ 第 5 次全局迭代仍有失败 → 暂停，报告用户                  │   │
│  │  ✅ 全部修复 → git commit → 进入 Phase 2                  │   │
│  └──────────────────────┬───────────────────────────────────┘   │
│                         │ 反馈：全量单元 PASS ✓                  │
│                         ▼                                        │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  Phase 2: E2E 功能/交互测试                                 │   │
│  │                                                          │   │
│  │  1. 编写 E2E 测试（如尚不存在）:                             │   │
│  │     • 覆盖完整用户流程（happy path）                         │   │
│  │     • 覆盖关键错误路径（error cases）                        │   │
│  │     • 验证响应格式合规性                                     │   │
│  │     • 文件: tests/test_e2e_<feature>.py                    │   │
│  │                                                          │   │
│  │  2. 运行 E2E 测试: pytest tests/test_e2e_*.py -v -s        │   │
│  │                                                          │   │
│  │  3. 全部 PASS → 进入 Phase 3                              │   │
│  │  4. 有 FAIL → 同 Phase 1 诊断修复流程                      │   │
│  └──────────────────────┬───────────────────────────────────┘   │
│                         │ 反馈：E2E 全 PASS ✓                    │
│                         ▼                                        │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  Phase 3: 交叉验证 & 汇总报告                               │   │
│  │                                                          │   │
│  │  1. 运行全量测试确认最终状态: pytest tests/ -v              │   │
│  │  2. 输出测试报告:                                           │   │
│  │     📊 测试报告                                             │   │
│  │     ├── 单元测试: N passed / M failed / K auto-fixed       │   │
│  │     ├── E2E 测试: N passed / M failed / K auto-fixed       │   │
│  │     ├── 修复迭代次数: X                                     │   │
│  │     └── 状态: ✅ 全部通过 / ⚠️ 需人工介入                    │   │
│  │                                                          │   │
│  │  3. 全部通过 → 进入 Step 4 归档                             │   │
│  │  4. 仍有问题 → 基于报告内容暂停询问用户                      │   │
│  └──────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

**自动修复优先级（从快到慢）:**

| 优先级 | 问题类型 | 自动修复策略 |
|--------|----------|-------------|
| P0 | import 缺失 | 自动 `pip install` / 补充 import 语句 |
| P1 | 测试断言值过时 | 读取实际返回值，更新断言 |
| P1 | Mock 签名不匹配 | 读取被 mock 函数签名，更新 mock 参数 |
| P2 | 简单逻辑 bug | 读取错误堆栈 → 分析根因 → 修改实现代码 |
| P2 | 测试调用方式过时 | 读取 API 变更，更新测试调用方式 |
| P3 | 复杂集成问题 | 暂停 → 报告用户具体问题 |

**暂停条件（停止自动修复，询问用户）:**

| 条件 | 处理 |
|------|------|
| 同一问题自动修复 3 次后仍失败 | 报告：问题描述 + 已尝试方案 + 失败原因 |
| 全局迭代 5 次后仍有失败 | 报告：剩余失败清单 + 修复历史 |
| 测试框架本身报错（非测试逻辑） | 报告：框架错误详情 |
| 修复导致新的测试失败 | 回退修复 → 报告冲突 |

**非暂停条件（自动继续）：**
- 首次修复后测试通过 → ✅
- 修复引入非破坏性警告 → ✅ 记录
- 不同失败原因的新失败（非修复引入）→ ✅ 继续修复
- E2E 测试文件不存在 → ✅ 自动创建并运行

### 🔵 Step 4: 归档 & 迭代

#### 4.1 完成开发

使用 `superpowers:finishing-a-development-branch`：
- 全量测试验证 → 展示合并/PR/保持/丢弃 4 选项

#### 4.2 OpenSpec 归档

```bash
cp -r openspec/changes/<change-id>/specs/ openspec/specs/
git add openspec/ && git commit -m "docs: archive specs"
```

#### 4.3 迭代判断

询问用户：**本轮目标达成？**
- ❌ 未达成 → 回到 🧠 Step 1（新 feature）或 🔵 Step 2（同 feature 续）
- ✅ 已达成 → 🎉

## 关键原则

| 阶段 | 交互模式 | 原则 |
|------|----------|------|
| 🧠 Brainstorm | **高交互** | 每次只问一个问题；苏格拉底式引导；绝不跳过用户确认 |
| 🔵 OpenSpec | **低交互** | 一次性审查确认；确认后锁死规范 |
| 🟢 Execute | **零交互**（除异常） | TDD Red-Green 循环驱动；全自动 subagent；只在阻塞时暂停 |
| 🔵 Archive | **低交互** | 仅确认是否继续迭代 |

## 违规 STOP 信号

| 信号 | 阶段 |
|------|------|
| 跳过 brainstorming 直接写 spec | 🧠 |
